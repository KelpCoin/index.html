GPU Fallback Plan

  1. Detect GPU health
    • Run a fast probe at startup (e.g., CUDA/ROCm device query or simple tensor op) and record driver/runtime versions.
    • Check for recent device errors (watchdog resets, ECC faults, thermal throttling) and GPU memory availability.
    • Expose a lightweight health endpoint/metric so schedulers can see GPU readiness.
  2. Switch workloads intelligently
    • Route latency-sensitive or heavy parallel jobs to healthy GPUs; keep small/batchable tasks on CPU when GPUs are saturated.
    • Use a per-job capability flag ("gpu_preferred", "gpu_required", "cpu_ok") to decide whether to fall back or fail fast.
    • When a GPU probe fails mid-run, gracefully checkpoint, reschedule on CPU, and throttle GPU retry frequency.
  3. Log and observe fallbacks
    • Emit structured logs with job id, node, GPU id, probe results, and reason for CPU fallback.
    • Count fallback events in metrics (e.g., Prometheus counter) and alert on spikes or repeated device failures.
    • Include timing data comparing GPU vs CPU execution to tune future scheduling decisions.
